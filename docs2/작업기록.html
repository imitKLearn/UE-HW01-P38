풀어야 했던 것

WBP_Title의 ServerIP 입력칸 하나가 두 가지 주소를 겸하고 있었다.

  • 웹서버 주소 — 로그인/회원가입 HTTP 요청의 대상
  • 게임서버 주소 — ConnectServer의 OpenLevel 대상

그래서 접속하려는 사람이 게임서버 IP를 말로 전해 듣고 손으로 적어 넣어야 했다. 이번 작업이 그 겸직을 풀고 IP 전달을 웹서버 경유로 자동화한다.

2. 확정된 설계 결정

결정근거
게임서버 IP는 UE가 ISocketSubsystem으로 직접 탐지해 전송웹서버가 request.client.host로 추정하면, 웹서버와 게임서버가 같은 PC일 때 127.0.0.1이 등록되어 다른 PC 클라이언트가 접속하지 못한다
등록 IP는 파이썬 모듈 변수에 보관DDL 실행이 필요 없다. 웹서버를 재시작하면 초기화되므로 죽은 서버 IP가 남지 않는다
최신 1개만 유지하고 /login 응답에 동봉새 조회 엔드포인트도, 서버 목록 UI도 필요 없다
WBP_Title에 GameServerIP 입력칸 신설아래 3절 참고. 칸 하나를 겸용하면 요구사항 1이 조용히 깨진다
등록 응답을 기다린 뒤 레벨을 연다실패해도 그냥 서버가 뜨면 등록됐는지 확인할 방법이 없다. 실패 시 InfoText에 표시하고 이동하지 않는다
포트는 등록하지 않는다게임서버는 UE 기본 7777이고 OpenLevel(IP)도 기본 포트를 쓴다
/register_server도 같은 AuthResponse 모델을 쓴다UE의 기존 {result, message} 파싱 경로를 그대로 재사용하기 위해서다

응답 계약 (기존 형식 그대로 확장)

{ "result": true, "message": "", "idx": 1, "nickname": "junios", "level": 1, "server_ip": "192.168.0.5" }

server_ip는 로그인 성공 시에만 의미가 있고, 등록된 서버가 없으면 ""다.

상황HTTPresultserver_ip
서버 등록 성공200true등록한 IP
등록 요청의 ip가 빈 값422—Pydantic min_length=1이 거부
로그인 성공, 등록 서버 있음200true그 서버 IP
로그인 성공, 등록 서버 없음200true""
로그인 실패200false""

3. 왜 입력칸을 하나 더 만들었나

처음 설계는 받은 게임서버 IP를 기존 ServerIP 칸에 자동으로 채우는 것이었다. 코드 흐름을 따라가 보니 깨진다.

ServerIP 칸은 Login(), SignUp(), 그리고 새로 만든 StartServer()가 웹서버 주소로 읽는 값이다. 여기에 게임서버 IP를 덮어쓰면:

  • 두 번째 사람이 로그인한다 → 칸에 남의 게임서버 IP가 채워진다
  • 그 사람이 StartServer를 누른다 → 등록 요청이 웹서버가 아니라 남의 게임서버로 간다
  • 요구사항 1이 깨진다
첫 로그인 때는 등록된 서버가 없어 칸이 바뀌지 않는다. 그래서 혼자 테스트할 때는 걸리지 않고 여러 명이 쓸 때만 터진다. 칸 하나가 두 주소를 겸할 수 없다고 판단해 GameServerIP 칸을 신설했다.

7. 진행 중 내린 판정

판정근거
A게임서버 IP를 UE가 직접 탐지한다위 2절. request.client.host는 웹서버와 게임서버가 같은 PC일 때 틀린 답을 낸다
BGameServerIP 입력칸을 신설한다위 3절. 원래 결정을 그대로 따르면 요구사항 1이 조용히 깨진다
CIntermediate/Build를 지우고 다시 빌드했다첫 빌드가 Result: Succeeded를 냈는데도 다른 디렉터리(L20260907)의 소스를 컴파일하고 있었다. 이 폴더가 그 프로젝트에서 복사돼 오면서 Makefile.bin·TargetMetadata.json·.rsp에 예전 절대경로가 박혀 있었기 때문이다. obj에 새 심볼이 없는 것으로 확인하고, 재생성 가능한 캐시(2.6GB)를 지운 뒤 다시 빌드해 실제 컴파일을 확인했다
DDB 이름을 seul → t0826db로 바꿨다사용자가 비밀번호를 알려준 뒤에도 Unknown database seul이 났다. 이 PC에 seul이 없다. member 테이블을 가진 DB를 찾으니 t0826db 하나였고, 스키마가 main.py가 기대하는 것과 정확히 일치했다(idx PK auto_increment, user_id UNIQUE, passwd, nickname, level 기본값 1). seul을 새로 만들지 않았다 — 같은 스키마가 두 개로 갈라지는 쪽이 더 나쁘다
EServer/.venv를 새로 만들었다이 폴더에는 가상환경이 없어 서버를 띄울 수 없었다. run.bat이 .venv\Scripts\python.exe를 찾으므로 없으면 사람도 실행하지 못한다
Fpytest를 도입하지 않았다선행 작업이 "pytest 미사용"으로 정해둔 것을 유지했다. DB 비밀번호를 받기 전에 쓴 스텁 검증 스크립트는 임시 폴더에서만 돌리고 프로젝트에 남기지 않았다
C에 딸린 부작용 — 판정 C를 알아채기 전에 Build.bat을 두 번 돌렸고, 그 두 번이 옆 폴더 D:\KM\K82\UE\P\L20260907을 빌드했다. 그 프로젝트의 소스는 건드리지 않았고 Intermediate/Binaries만 재생성됐다.

8. 남은 일 — 사람이 직접

서버·DB·컴파일·위젯 배치는 끝났다. 남은 것은 PIE 실행뿐이다.

사전 준비: Server\run.bat 실행. 계정은 tester2 / 1234, 웹서버 주소는 127.0.0.1.
